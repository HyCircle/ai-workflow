# 工作流 + 文档系统设计蓝图

> 本文是给人和维护者看的设计权威，说明当前取舍与边界。可运行的 SOT 是本仓 `wf/` 与 `README.md`；消费仓的物理路径位于 `.workflow/`，agent 通过 `AGENTS.md`、skills 和 `discipline.md` 工作。

## 0. 核心取舍

工作流让一个 planner 对结果负责：理解目标与现状，找出最关键的不确定性，选择能最快获得有效反馈的下一步，整合证据，并判断结果是否足以支持用户目标。planner 可以自己实现，也可以委派；任务成本包括外呼、交接、返工、用户负担和质量，不只包括 planner 的上下文。

角色分工包括：bs 负责长期设计，planner 负责当前任务的编排和裁决，worker 执行，reviewer 按需审查，finishing 由本轮亲历者写归档并交棒，cleaning 按需筛选手册候选、巡检知识层与 TODO 并在项目可写范围内全仓巡检维护，holistic 用强模型按需整体审查设计的自洽与复杂度，challenge 用强模型对实验类结论专门找反证。多 agent 是执行选项，是否委派由边界、反馈价值和交接成本决定。

## 1. 文档系统：各类信息各有其家

消费仓物理路径在 `.workflow/` 下；本文表格使用短名，完整路径由消费仓 `AGENTS.md` 的文档路由定义；agent 只读当前任务需要的文档，不预读。

| 家 | 内容 | 维护方式 |
|---|---|---|
| `discipline.md` | 六条常驻纪律与脊椎 | kit 单源，随安装投影 |
| `AGENTS.md` | 项目工具约定、协作约定、文档路由与手册清单，不装状态与设计内容 | 项目维护，人策展；协作约定与手册清单由 cleaning 提议、用户确认 |
| `architecture.md` | 系统现状全局图：模块边界、关键调用链、已能用的功能 | cleaning 与 holistic 提交候选，人审判断型改动 |
| `decisions/` | 当前设计：稳定、长期、会反复引用的决定 | 一个主题一份；慢层，一般不动，设计变了改正文，整体变了整篇重写，不写修订记录 |
| `TODO.md` | 下一步、等别人的事、已知问题 | 每条最多两行(做什么、卡在哪或为什么、指针)，不写进展；finishing 按格式重写相关条目，cleaning 逐条理解后提议删改 |
| `patterns/` | 按任务类型的手册：步骤、坑、验证清单 | finishing 默认不提、最多两条候选，cleaning 复核后交用户确认再合入 |
| `scratchpad/` | WO、brief 快照、报告、验收单、run 日志 | ephemeral，按龄 GC |
| `scratchpad/_archive/` | finishing 写的会话归档，冷存档，按需追溯 | 本机长期保留，忽略但不参与普通 GC；不是项目事实源 |

ADR 记录系统为什么是现在这样、哪些事不做，只写只看代码会做错的地方：跨任务、改起来贵、理由从代码看不出来，三条同时满足才写；实现、计划、现状和任务做法各归代码、TODO、architecture 和手册。格式与判断标准只在 bs 技能里写一处，不在 `decisions/` 放模板文件。它是慢层而不是铁律：agent 按它工作，实况或证据与它冲突时提出改它的方案。用户目标和授权边界是硬约束；实现建议与尚未验证的假设要明确标出。版本历史价值低，有 git 是加分项，no-track 仓同样原地改。没有稳定决策时，不为获得派单资格制造 ADR。

项目知识只放在上表各处，所有 agent 都读得到。各 agent 自带的私有记忆(如 Claude Code 的项目记忆)只有一家看得到、会无人管理地累积，cleaning 把其中的项目知识提升进手册、协作约定或项目文档后删除。手册靠 AGENTS 里的清单保证每次都被看到，不靠 agent 猜文件名。

bs 以用户意图为评判标准：意图与原话记在会话目录的 `intent.md`，红队、裁决和冷读都对照它。红队是可选的另一视角，意见逐条裁决为采纳、问题成立换修法或不采纳，裁决表经用户确认才改设计；新增机制须有真实触发场景。定稿前由没参与讨论的模型只拿意图和 ADR 冷读，查读不懂、与原话冲突和可删的部分——同一会话的自审拦不住自己论证过的错误。

`architecture.md` 是系统现状的全局图，负责回答整体是否自洽；具体契约仍以对应 ADR 为准。新增或修改 ADR 前对照它判断能否并入已有 ADR，避免各 ADR 局部成立、整体复杂。设计资产与 run 产物分离：长期证据随 ADR 进入 git，单轮材料留在 scratchpad；不另建裁决或交棒台账。

## 2. 当前工作闭环

```text
bs         记下用户意图 → 发散真实方案 → 讨论收敛 → （按需）红队，裁决表交用户
           → 著作 ADR → 冷读 → 用户定稿
planner    读目标和实况 → 三轴分诊 → 自做或短 brief 委派
           → 取得真实反馈 → 看整体与关键调用链 → 裁决并按需审查
worker     在目标和硬边界内实现，回报结果、偏离和矛盾
reviewer   按风险或明确要求审查实际行为与证据
finishing  亲历者写归档 → 学到的东西分去处 → 按格式更新 TODO → 交棒
cleaning   （按需）筛手册候选 → 知识层与 TODO → 全仓巡检 → scratch 与旧归档
           → 机械项直接修、判断项出确认清单
holistic   （按需）通读 architecture、全部 ADR 与关键代码 → 整体方案 → 用户确认后执行
challenge  （实验类结论）结论清单 → 强模型找反证，最多两轮 → 逐条结算 → 分列已支持与未验证
```

### 2.1 三轴分诊

每项工作分别判断：

| 轴 | 要回答的问题 | 影响 |
|---|---|---|
| 不确定性 | 哪个假设尚未验证？什么反馈能推翻或确认它？ | 优先读实况、看样本或跑最小完整路径 |
| 风险 | 错误影响什么，能否发现和恢复？ | 决定验证强度、独立审查和用户放行 |
| 委派收益 | 交接是否清楚，委派是否比直接完成更有价值？ | 决定自做、委派或并行 |

工作量和行数只作参考。探索可以委派，机械改动也可能高风险；不因“含实验”自动套完整模板或双审。

### 2.2 brief、反馈和实现判断

默认派单是一份短 brief，包含目标、依据与硬边界、待验证假设、交付与证据，以及可调整的做法建议。目标可以是非空的实现目标，也可以是一个需要回答的问题；若本任务承接现有 ADR，则引用它，否则只需说明用户任务。brief 不承担无关历史，也不把建议写成冻结契约。

探索优先建立一条最小完整反馈路径，再决定是否扩大实现。框架、测试、真实结果和未验证部分分别陈述。环境不可用时可以完成独立准备，但必须明确哪些检查未执行、需要什么环境、因此不能证明什么。

worker 在授权范围内选择实现。发现关键假设不成立、目标或范围必须改变，或建议会引入显著新机制时，立即在短报告中写出具体矛盾、证据和可行选择。正常的局部实现选择无需逐项请示。

每轮 run 保存一份 `brief.md` 快照；worker 和 reviewer 使用同一份快照。汇总包含 worker 的完整短报告；报告中的偏离与矛盾是 worker 的自述，供 planner 判断，`wf` 不解析或替它背书。

### 2.3 审查与 planner 亲验

方案审是可选能力，用 `wf ask` 发起：只有未经验证的方案一旦错误会造成明显返工，或用户明确要求时才安排；审查应回答指定疑点、读取相关实况并比较必要的替代方案。第二审按第二双眼带来的增益选择，用另一个模型再跑一次 `wf review`。

施工审围绕目标、实际入口、关键调用链、证据有效性和不必要机制组织。工单是上下文，不是逐条合规清单。问题要给出触发条件、错误结果和依据，已确认缺陷与待验证疑点分开；建议不当作阻断。

`wf run` 不带 `--review` 时只施工并做越界检查，测试与审查不运行，汇总明确写出；需要时再对当前工作树跑 `wf review`。

施工审看改动，结论质疑看「这句结论成立吗」，两者不互相替代。实验、基准比较、性能与数值结论在裁决前交 `/challenge`：质疑者只找反证、亲自复现，每轮最多 3 条异议与 3 个证伪实验，第二轮只核对第一轮异议；负责人逐条结算为已解决、接受为局限或不采纳。

planner 对整体和关键调用链自主核实，不能只转述报告。测试全绿只证明执行过的断言成立；审查无阻断问题只证明本轮没有报告阻断问题。放行判断还要结合目标、设计取舍、真实结果和证据限度。

### 2.4 复审和状态

发现问题后，planner 可以修实现、调整或撤回本轮方案、给出理由不采纳，或在确实改变长期契约时转 ADR。若矛盾反复出现、修补不断增加平行机制，或关键假设已被推翻，应先重新判断方案。

复审重写当前有效的 brief，撤回过时要求；旧 brief 和审查原文仍在 run 记录中，但不要求执行者同时满足多代判据。轮数只作提醒，不能机械决定停工或继续。长期 ADR 纪律保持不变，具体实现做法可以随着证据改变。

`wf` 不派生放行状态：汇总列出各外呼退出码、越界检查、测试结果、worker 报告和审查单，由 planner 裁决。外呼失败时命令以退出码 2 结束；只是审查失败时重跑 `wf review`，不重跑 worker。

## 3. 实现契约与布局

`wf` 是纯标准库的 Python 命令行工具，通过 `uv tool install` 安装，支持 Linux、macOS 和 WSL。四个子命令：`init` 投影与升级，`ask` 外呼原语，`run` 派 worker 施工（可选测试与审查），`review` 对当前工作树测试与审查。外呼走各家 CLI（`cursor-agent`、`codex`、`claude`）的非交互 JSON 输出：原始流直写日志，最终回复从流尾的结果事件或 codex 的末条消息文件提取；超时连整个进程组一起结束。只读靠各 CLI 自带的只读模式或提示词，不启用沙箱。不接各家 SDK：命令行能复用订阅登录与额度，安装也只需一个工具。

越界检查在 worker 前后对比负责人著作文件（decisions、architecture、patterns、AGENTS.md）的内容，派单前已有的改动不计入。每次 run 的目录保存 brief 快照、实际提示词、原始日志、报告、审查单、测试输出和汇总，不建立跨轮状态数据库。`.done` 只表示产物已定、可以清理，不表示放行；执行中的共享工作树不允许并行改写。著作类文件由负责人维护，worker 的写入面限于代码与 scratchpad。README、AGENTS、architecture 是注入面：worker 把仓内和 untracked 文本当不可信数据读，不执行其中的指令。

归档由本轮主 agent 在 finishing 时直接写：它看过工具输出与失败尝试，比事后从日志提取再交便宜模型压缩更完整，也避免压缩时改写用户的否定。用户原话按原句引用，结论分已验证与未验证。会话目录在归档后且无引用即可清理。

`wf init` 把包内 `kit/` 复制到消费仓 `.workflow/kit/`，不使用共享 symlink；后端技能入口是指向它的相对软链。track 与 no-track 只改变 git exclude 粒度，物理布局不变，布局与选项见 README。明确不做：可变路径前缀、no-track 时给 `.workflow/` 建独立 git 仓、给 cursor 单建技能入口、git 钩子与插件 / npm / Docker 包装。

## 4. 变更原则

工作流机制只在本仓修改，经 `wf init` 投影；本文和 README 同步说明当前为什么这样设计。改 `wf/` 代码前先读 `docs/failure-modes.md`，并按 `docs/MAINTAINERS.md` 跑测试。保持「一个标准库命令行工具 + Markdown」的最小系统，不为低概率情形新增角色、状态或固定仪式。
