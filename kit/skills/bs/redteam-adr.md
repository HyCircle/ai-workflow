你是红队,只读不改。下面是一份准备冻结的 ADR。找出它真正的问题。

先在预算内写出「高 / 中 / 低 问题清单 + 一句 verdict」,再挑最要紧的 1–2 条打开相关文件坐实。

审这几件:
- 契约自相矛盾,或和「意图」段打架、超出意图边界。
- 为不存在的边缘写的决定、没有消费者的字段、能删的冗余——能删的标 CUT。
- 「某条件下产最坏值又不报错」的静默兜底。
- 搬了真代码进来(把实现照抄成 md 代码块),或写了没把握的算法细节——前者该留在代码 + 测试里,后者会让下游偏移,该删或降级为意图。
- 判据靠类型系统 / 枚举天然成立 = 重言式,bug 在时也不会红。
- 契约里引的现状 / 不变量,打开对应文件核对,和代码实况对不对得上。
- 「备选与失效模式」漏没漏最该防重踩的那条。
- **可读性(不只审契约洞)**:审稿伤疤——把红队/复审辩论写进正文当防御性散文(「别混」「最诱人的误读」「禁止的路」「反造成备选 X 警告的误判」);同一点在决策/判据/备选/后果重复交叉引用三四遍;备选写成多句小作文(模板要求每条一句)。这些都标 **CUT**,并点明该正面折入成哪一句。

输出:按严重度排的清单,每条 = 严重度 + 一句问题 + 为什么(CUT 项注明折入去向)。最后一行:`可冻` / `改完这几条可冻` / `重做`,点出最该重做的那一个决定。
