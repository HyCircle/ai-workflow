# BS(脑暴)

你负责一个设计问题从发散到定稿。评判一切方案和意见的标准是**用户的意图**；外部模型提供另一种视角，取舍由你和用户决定。全程用清晰易懂的中文，术语就地说明。

## 开工

先读 discipline 和 AGENTS，再读 architecture 中相关部分与相关 ADR(按文件名挑)。本 session 的产物放 `.workflow/scratchpad/BS-<id>/`，`<id>` 为完整 session UUID。

## 1. 记下用户意图

建 `intent.md`：要解决的问题、用户的目标，以及用户的硬约束、拍板和否定(引原话)。讨论中用户每次纠正或拍板都补进去。它是红队、裁决和冷读共同的依据，也是你判断"这条意见该不该收"的尺子。

## 2. 发散

写 `options.md`：

- 至少 3 个真正不同的方案(不是一个方案换参数)，各用最强的论证去支持；
- 每个方案写清它在什么情况下会错；有更简单的路子一并写出；
- 列出假设与未知，标出哪些选择要先拿数据或小实验才能定；
- 最后写你的倾向和理由。

把方案讲给用户，一起讨论收敛。

## 3. 红队(按需)

设计面大、事后难改，或你和用户都拿不准时，向用户说明理由，经同意后请一次红队；小问题和已经讨论清楚的问题不请。对象是方案册或 ADR 草稿，一般只请一轮。外呼走后台，完成通知到了再读：

```bash
wf ask review .workflow/kit/skills/bs/redteam.md \
  .workflow/scratchpad/BS-<id>/intent.md .workflow/scratchpad/BS-<id>/options.md \
  --out .workflow/scratchpad/BS-<id>/redteam.md
```

审 ADR 草稿时把最后一个输入换成 ADR 文件。

## 4. 裁决红队意见

逐条核实后给出处理，列成裁决表交用户：

| 处理 | 含义 |
|---|---|
| 采纳 | 问题成立，按它改；写明改动落在哪个决定 |
| 问题成立，换修法 | 问题成立，但它建议的修法与用户意图或纪律不符；写明你的修法 |
| 不采纳 | 写理由 |

裁决依据：

- 对照 `intent.md`。红队指出目标系统本身的缺陷时，先看用户意图是要暴露它还是规避它。
- 对照 discipline 脊椎。新增机制、兜底或流程要有真实会触发的场景。
- 只改措辞的意见直接采纳，表里一行带过。

用户确认裁决表后再改方案或 ADR。

## 5. 著作 ADR

ADR 记录"系统为什么是现在这样、哪些事不做"，只写只看代码会做错的地方。它是慢层：定下一般不动，设计变了改正文，整体变了整篇重写，不再适用就删除并清掉各处引用。agent 按它工作，与实况冲突时提出改它的方案。

**什么值得写**——同时满足：

1. 跨任务：以后很多次工作都会碰到它；
2. 改起来贵：要动很多地方或要和别人重新对齐；
3. 理由看不出来：只读代码的人很可能顺手改掉它，或重走已经否掉的路。

**其余各有去处**：实现细节、配置值、规则条文 → 代码、配置和测试；计划与进度 → TODO；系统现状 → architecture；做某类任务的步骤和坑 → 手册。一个项目通常十份左右，每份一两页；超出多半是混进了实现，或同一主题拆成了几份。

**先并入再新建**：同一主题改原 ADR，确属新主题才新建。

**格式**：文件 `.workflow/decisions/NNNN-<英文短名>.md`，`NNNN` 取现有最大号 + 1，四位，从 `0001` 起。有长期证据(实验数据、notebook、一次性脚本)时建同名文件夹 `decisions/NNNN-<短名>/`，主文件与文件夹同名，附件放在一起。

```markdown
---
id: NNNN
title: <一句话结论，陈述句>
date: YYYY-MM-DD        # 最近一次修改日期
status: proposed        # proposed | accepted
tags: []                # 领域标签，如 [auth, storage]
---

# ADR-NNNN: <与 title 一致>

## 意图
<2–3 句：为什么要这个决定，对用户有什么价值，边界在哪。>

## 背景与约束
<现状、硬约束；决定靠数据支撑时写结论，原始数据放同名文件夹。>

## 决策
<边界、不变量、硬上限、明确不做的事。可用散文、格式样例、接口签名、伪代码；
换一种实现仍成立的才写这里。需求没定的写一句"待定"。>

## 备选与失效模式
<没选的做法，每条一句："若选它会怎么错"。>

## 后果
<代价、收益、新约束。>
```

**写法**：

- 正文只写现在的设计，不写修订记录、讨论过程和事故经过；审稿意见采纳后直接改写对应的决定。
- 写设计，不写计划："先做哪部分""开工前确认什么"放进 TODO 或交棒。
- 需求还没定的部分写一句"待定"，不为它设计预案。
- 句子一句一事，用用户和团队日常的说法；同一事实只写一处，其他地方引用。
- 不搬真代码。引用写 `ADR-NNNN` 或稳定的契约名、节名，不引用 scratchpad，不写文件行号。

## 6. 冷读，交用户定稿

新建或大改的 ADR，冻结前交一个没参与讨论的模型冷读，只拿 `intent.md` 和 ADR：

```bash
wf ask review .workflow/kit/skills/bs/coldread.md \
  .workflow/scratchpad/BS-<id>/intent.md .workflow/decisions/NNNN-<slug>.md \
  --out .workflow/scratchpad/BS-<id>/coldread.md
```

按冷读结果改掉读不懂的句子、与用户原话冲突的决定和可删的段落。然后向用户简短呈现：目标、具体决定、依据、主要取舍、未验证部分，以及冷读改了什么。用户同意后把 `status` 翻为 `accepted`。

## 7. 交棒

落地交 `/planner`，带上 ADR 与待验证的问题。
