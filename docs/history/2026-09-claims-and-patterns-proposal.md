# 提案：结论质疑与任务手册——把质量把关放到真正出错的地方

状态：已实施并归档（2026-09-30）。现行做法见 `wf/kit/` 与 README；本文保留当时的证据与推理。其中「AGENTS 当前状态一节」与 `doctor` 未采纳：状态归 TODO 与 architecture；`doctor` 暂不做。

**核心判断：这套工作流的质量短板不在编排，而在两处空白。一是没有人专门质疑“结论是否被证据支持”，现有审查看的是 diff；二是会话里学到的教训没有一个下次做同类任务时一定会读到的地方。** 对照测量里，自由使用和 `/planner` 在同样几处过度声称，便宜模型的 diff 审查也没拦住一个真实 bug；而一个带着“找反证”任务、会亲自跑检查的强模型评审，把这些问题都找了出来。

改进优先做三件事：**实验和研究类结论必须经过有界的质疑并结算；把被采纳的教训写进按任务类型组织的手册；让文档里的结论带上审核状态。** 其余机制保持不变。

## 1. 证据

### 1.1 实际使用情况

以下数字来自三个消费仓的 Claude Code 会话日志和 36 份会话归档：

- zhidazhushou 的 53 个会话中，`/planner` 显式调用 6 次，`/bs` 2 次，`/finishing` 14 次。用户近期主要是自由使用加先读 discipline，finishing 和 cleaning 用得最多。
- 最近 6 份归档里没有派单。留下的 run 全是 `review_skipped`。`run_worker.sh`、状态派生和双审等约 1900 行机制，大部分时间处于闲置状态。
- 冷启动要读的文档偏大：hubpage 的 `architecture.md` 约 54KB，开场合计约 61KB；zhidazhushou 约 32KB，另有 ADR 共约 79KB。
- 会话里得出的“稳定但未冻”候选决定，在归档中出现 12 次，之后没有固定去处。例如 hubpage 发现的“WSL 上低端口不会立即拒连”，只存在于测试代码里。
- 2026-09-22 的自审已经发现，低成本模型压缩对话时会反转用户的否定、漏掉拟议提交消息（该审视记录已删除，见 git 历史中的 `docs/history/2026-09-workflow-review.md`）。

### 1.2 对照测量

**任务**：MLM optimizer rollout 的 Step 3，基线提交 `112a762`。选它有两个原因：历史上这次执行用的是 `/planner`，结论事后被独立审查判为“明显偏乐观”，10 条问题逐条复现属实；那份审查可以当评分依据。历史上那次 `/planner` 会话一次都没有派单，全程是主 agent 自己完成的。

**设置**：
- 两组各用一份隔离副本。副本只包含 `112a762` 及之前的历史，并还原了当时不在 git 里的上下文：`AGENTS.md`、TODO、`workflow.env`、01–03 号归档、ADR 0000–0003、测试依赖的 scratch 文件和重新生成的 baseline。9/14 之后改过的 ADR-0004、`architecture.md` 和一份项目状态 memory 没有放入，避免泄题。
- 两组都在 bubblewrap 沙箱里无头运行 `claude-opus-5-5`，看不到真实项目目录和其他会话记录。
- 开场提示相同，只差是否带 `/planner`。用户当年在会话中途的三次回复，改为提前交代。
- 组别随机分配，两组先后运行，避免计时互相干扰。
- 评分者是 cursor-agent 上的 `claude-opus-5-5-medium`，分两轮：第一轮盲评且不给参考答案；第二轮再对照历史独立审查逐条核查。评分者自己写了二十多个检查脚本去复现关键结论。

**结果**：

| | 自由使用 | `/planner` |
|---|---|---|
| 用时 / 主 agent 花费 | 16 分钟 / $4.19 | 21 分钟 / $3.28，另加一次 Grok 审查 |
| 做法 | 自己完成 | 自己实现，未派施工；最后 `REVIEW_ONLY=1` 交 Grok 审查，无 blocking |
| 第一轮六项得分（满分 5） | 5 / 4 / 4 / 4 / 4 / 4 | 4 / 3 / 3 / 3 / 4 / 3 |
| 第二轮“结论与证据匹配”调整后 | 3 | 3 |

- 自由使用组略好，差距中等偏小。它发现 collision 案例对 1e-15 量级的扰动敏感，改用 10 个扰动起点比较；在实测中遇到区间导数出现 Inf，并修正了导数公式。
- `/planner` 组措辞更克制，但保留了导数 bug，把由此引起的失败误诊为“Fisher 曲率发散导致 rank loss”，并把测试断言放宽到接受 `numerical_failure`。Grok 施工审没有发现这个问题。
- 自由使用组做出了一条错误的因果结论：“剩余 gap 是 strict domain 的极限”。评分者用 barrier 方法在它自己的 evaluator 上达到了那个上确界。
- **两组都重犯了历史审查指出过的几类错误**：
  - 都写了“corpus 里没有触发 D-inverse 门”，实际 `binary_separated` 的 290 次求值中有 253 次被拒。
  - 都把“15/17 个 regular 例”和“与独立 reference 差距 7.4e-11”写在一起，实际只有 5 个案例有独立 reference。
  - BFGS 的比较口径都不公平：停止条件不同、做了多余的 QR 求解、预算名实不符，报告的倍数被夸大约一倍。

**限度**：只有一个任务，每组只跑一次，任务本身对扰动敏感，噪声大。评分者与两组同属 Opus 家族，可能存在同家族偏好，但对两组的影响相同。盲评不完全：一组的汇报提到了 Grok 审查。历史环境是近似还原的。本机实验材料位于 `/home/yh/ab-eval/`，不承诺长期保留；影响结论的事实已写在本节。

### 1.3 由此得出的判断

- 过度声称在两种模式下都会出现，并非由委派或编排引起。原因是没有一个环节专门检查“这句结论成立吗”。
- 施工审（审 diff）和结论质疑是两件事。前者在这次没有拦住真实 bug，后者找出了两组汇报中最需要修改的地方。
- `/planner` 的角色设定在这一次里没有带来可测的收益。只凭一次测量不改它，但本提案的新机制不依赖 `/planner`：用户实际在自由使用，新能力必须在自由使用时也能调用。
- 两组重犯的错误，历史上已经被指出过。教训写在归档对话和项目文档里，做同类任务时不会被加载。

## 2. 从两个外部仓库借什么

| 来源 | 机制 | 对应问题 | 借法 |
|---|---|---|---|
| research-bridge | 研究契约：假设、要测的量、实验设计、替代解释、证伪条件、分析计划、决策规则，动手前审一次 | 比较口径不公平、弱证据也能拍板 | 可选的契约模板和契约审查 |
| research-bridge | 结果声明带性质标签（有利 / 无效 / 不利 / 无定论 / 仅证明可行）和局限清单 | 把几个结论混成一个“有利”结论 | 结论清单格式 |
| research-bridge | 结论质疑者（RVA）：只找反证；最多 3 条异议、3 个有界证伪实验、2 轮；第二轮只核对第一轮异议 | 过度声称、审查无限扩张 | `/challenge` 技能 |
| research-bridge | 结算：分列已支持与不被支持的结论；每条异议标“已解决 / 接受为局限 / 不采纳”并附证据 | 汇报把未验证写成已验证 | 结算格式，进入汇报和文档 |
| research-bridge | 执行类任务可按机器证据自动收尾，研究类任务不允许自动收尾 | 重流程用错地方 | 只对实验和研究类结论启用质疑 |
| research-bridge、mex | 结论须经审核才成为权威知识；历史材料只作候选 | 错误结论被文档一层层继承 | 文档结论标审核状态 |
| mex | 按任务类型组织的手册（步骤、坑、验证清单、排错）和 GROW 沉淀步骤 | 教训没有下次会读到的去处 | `.workflow/patterns/` |
| mex | VERIFY 要求逐项列出清单项及是否通过 | 抽象原则难以执行 | 手册的验证清单逐项回报 |
| mex | ROUTER 的“当前项目状态”（能用的 / 未做的 / 已知问题，各 3–7 条）加按任务加载的路由表 | 冷启动全读大文档 | AGENTS 增加当前状态与路由 |

不借的部分：两个仓库的 MCP 服务、SQLite 状态库、哈希绑定链、tunnel、代码图谱、Hub、成员系统和遥测。这些都会显著增加机制体积，而本仓的约束是保持“bash + Markdown + 一个安装脚本”。mex 的 grounding 依赖 tree-sitter，不支持 R，只借“结论绑定代码位置、代码变了就复核”这个思路。

## 3. 改进方案

### 3.1 结论质疑：新增 `/challenge` 技能

**适用范围**：实验、基准比较、性能结论、数值精度结论，以及任何形如“X 比 Y 好”“问题不存在”“已验证完成”的结论。普通编码任务不需要它。它可以在自由使用时直接调用，也可以由 planner 在裁决前调用。

**流程**：

1. **写结论清单**。由主 agent 写到 `.workflow/scratchpad/<会话目录>/claims.md`。每条结论包含：
   - 结论原文；
   - 性质：有利、无效、不利、无定论、仅证明可行；
   - 证据：文件、命令、数据位置；
   - 已知局限；
   - 结果对应的提交号，以及生成时工作区是否有未提交改动。
2. **外呼质疑者**。通过 `call_agent.sh` 调用强模型，模型取自新配置项 `WF_CHALLENGE_MODEL`。质疑者可以运行代码做核查，但产物只写在 scratchpad 下，不改仓库。
3. **质疑者的规则**，写在 `kit/skills/challenge/challenger-preamble.md`：
   - 只找能推翻或显著削弱结论的证据，不做确认性搜索，不审代码风格，不提出新的研究方向。
   - 每条异议写明：影响哪条结论、依据是什么、解决它最少需要什么证据；亲自复现过的要标明。
   - 最多 3 条实质异议、最多 3 个有界的证伪实验。所有意见在本轮一次提完。
   - 第二轮只判断第一轮异议是否解决，不提新意见。两轮用完，质疑者的阻断作用结束，但这不证明结论成立。
   - 输出沿用现有 sentinel 块格式，字段为结论编号、异议、影响、最少证据、是否复现。
4. **结算**。主 agent 对每条异议给出三种处理之一：已解决（附新证据）、接受为局限、不采纳（附理由）。最终汇报和写入文档的结论，必须分列“已支持的结论”和“不被支持或未验证的结论”。

**模型选择**：用强模型，不用便宜模型。对照测量里有效的是同家族的 Opus 5.5 评审，所以异家族不作为硬要求。默认值取当前最强的可用档，由 `workflow.env` 配置。

**成本**：一次质疑大约相当于一次强模型审查。只在实验和研究类结论上启用，普通任务不增加开销。

### 3.2 可选的实验契约

在 `kit/skills/challenge/contract-template.md` 提供契约模板，字段为：问题、假设、要测的量、候选与比较口径（起点、停止条件、预算、计时范围、reference 的数量与来源）、替代解释、证伪条件、决策规则。

需要跨多个候选做比较、或结论会影响默认实现时，先写契约，再用 `/challenge contract` 让质疑者只审口径和决策规则，然后再动手。对照测量里 BFGS 口径不一致、“Armijo 是否值得替换”的证据门槛，都属于应在契约阶段解决的问题。

### 3.3 任务手册：`.workflow/patterns/`

- **格式**：每份手册对应一类可复现的任务，含四节：步骤、坑、验证清单、排错。文件头写适用的任务描述。`AGENTS.md` 文档地图增加 `patterns` 一行，冷启动时按当前任务查找匹配的手册。
- **来源**：只从真实失败中来，符合 discipline 的“有真实触发路径才加”：
  - 结算中“已解决”或“接受为局限”的异议；
  - 用户的纠正；
  - 实测踩到的环境坑。
- **写入时机**：
  - finishing 交棒增加“手册更新候选”一项，取代现在无去处的“稳定但未冻”候选；
  - cleaning 把候选合入对应手册，同类条目合并；
  - 能构成长期设计决定的，仍按现有流程写 ADR。
- **使用方式**：做匹配的任务时，按验证清单逐项回报是否通过，不做概括。

例如一份“optimizer 候选比较”手册，验证清单里会有：各候选停止条件与预算一致；写明独立 reference 的实际数量；对扰动敏感的案例用多起点；结果对应已提交版本；跑一次打包检查。

### 3.4 文档结论带审核状态

- 设计文档、证据文档和 ADR 的“依据”部分，引用实验结论时注明是否经过 `/challenge` 结算。未结算的结论写作“待验证”，不写成事实。
- cleaning 的文档维护增加一项：检查结论引用的代码位置在该结论之后是否改过，改过的列为待复核。
- 旧文档里的结论不批量回溯标注，只在任务涉及时就地处理，处理方式与 research-bridge 的历史迁移一致：旧材料只作候选。

### 3.5 冷启动与交棒

- **`seed/AGENTS.md`** 增加“当前状态”一节：能用的、未做的、已知问题，各 3–7 条。cleaning 负责维护。冷启动顺序改为 discipline → AGENTS（含当前状态）→ 与任务相关的 patterns、ADR、architecture 章节，不再默认通读 architecture。
- **finishing 交棒**固定包含以下内容：
  - 结果与验证范围；
  - 已支持与未验证的结论；
  - 手册更新候选；
  - 下一步；
  - 观察到的仓库状态：分支、HEAD、是否有未提交改动、实验结果对应的提交；
  - 开场提示词。
- 交棒写入会话后再提取 transcript，解决提取时交棒尚未刷入日志的问题。

### 3.6 discipline 的措辞

第 5 条补一句，表达“结论强度不超过证据”：比较实验须口径一致；结论与证据的对应关系要写出来，未验证部分和已验证部分分开陈述。脊椎的“默认不加”增加一句：验证和质疑不属于默认不加的范围。discipline 仍保持短小，具体做法放在 `/challenge` 和手册里。

## 5. 明确不做的事

- 不引入 MCP 服务、数据库、哈希绑定链、代码图谱、Hub 或成员系统。
- 不给每个任务都加质疑环节；普通编码任务保持现有流程。
- 不再增加审查轮数或审查员。质疑者有明确的轮数和异议数上限。
- 不据一次测量删改 `/planner`、`run_worker.sh` 或施工审。它们的去留等更多测量结果再定。
- 不批量回溯旧文档。
- 不把对照测量做成独立产品；评测流程写在维护文档里，复用隔离副本与盲评，不另建评测平台。

## 6. 实施顺序

1. **`/challenge` 与契约模板**。外呼用锁定的只读调用形状（第 8.1 节）。先在本仓实现，用本次对照测量的 MLM 副本做验收：在自由使用组的产出上跑一次 `/challenge`，检查 1.2 节列出的几类过度声称是否在结算前被指出。
2. **patterns 与 finishing/cleaning 调整**。随第 1 步第一次真实使用产生第一份手册，不预先编写空手册。
3. **AGENTS 当前状态、冷启动顺序、discipline 措辞**。
4. **安装卫生与 doctor**（第 8.2、8.3 节）。可与第 1 步并行，不阻塞质疑能力。
5. **再测一轮**。用同一套隔离与盲评方法，在另一个任务上比较“自由使用”与“自由使用加 `/challenge`”，候选任务是 hubpage 测试瘦身（基线 `4164e35`，参照 `b54300a`）。评测步骤按第 8.4 节固化。

涉及脚本时按 [MAINTAINERS](../MAINTAINERS.md) 跑 `bash kit/scripts/tests/run-all.sh`。

## 7. 如何判断有效

- 主要看最终汇报和写入文档的结论里，过度声称是否减少。用盲评对照测量，评分者看不到组别。
- 同一类错误是否在手册建立后不再重犯。
- 一次质疑的花费和用时，是否与它拦下的问题相称。
- 不以异议数量作为质量指标：异议少可能只是查得少。

## 8. 基础设施：借什么、不借什么

机制层借的是“质疑结论”和“沉淀手册”。基础设施层两边都有完整产品栈，大部分不适合本仓的约束（bash、Markdown、一个安装脚本）。值得借的是几条边界，不是服务形态。

对照本仓现状：`call_agent.sh` 已有超时、整树回收、流式落盘和凭证打码；`install.sh` 已把机制副本与项目文档分开；scratchpad 已与 ADR 分离。缺口在外呼的真实隔离、安装时对用户文件的破坏，以及装完之后无法自检。

### 8.1 research-bridge：外呼边界

| 设计 | 他们怎么做 | 本仓现状 | 是否借 |
|---|---|---|---|
| 默认只读、默认断网 | Codex 任务默认 `read-only`，`networkAccess=false` | Cursor 只读模式用 `--mode ask`；Codex 无论是否只读都走 `--dangerously-bypass-approvals-and-sandbox` | **借。** 质疑者和施工审必须是真只读。Codex 只读改走沙箱；需要写工作区或联网时，任务请求和主机配置同时允许才开（双重许可） |
| 质疑者的调用形状锁死 | RVA runner 只接受固定参数向量：`--print --no-session-persistence --disable-slash-commands --tools Read,Glob,Grep --permission-mode dontAsk`，外加 JSON schema | `call_agent.sh` 只改审批模式，工具集不收窄 | **借。** `/challenge` 单独一条调用路径，只给读文件、搜索、跑检查的能力，产物只允许写 scratchpad |
| 会话断开不等于取消任务 | 独立 worker + 目录租约（pid + 心跳） | 长外呼已用宿主后台执行；单用户、单工作树 | **不借租约。** 后台执行已经够用 |
| 证据绑到仓库状态 | 每条审计事件记录 `repo_commit` 和 dirty 文件列表；机器证据带 `run_id` + `generation`，过期标 `STALE` | run 目录有 brief 快照；对照测量里有一组 CSV 标着 `dirty=TRUE`，结论对不上已提交版本 | **借字段，不借哈希链。** 质疑报告和交棒写上 HEAD 与是否有未提交改动 |
| 路径不出仓 | `resolveInside` 拒绝绝对路径和 `..` | `check_docs` 已 fail-loud 定位仓根 | 保持现状 |
| 读写上限 | 读文件、搜索、diff 有字符和条数上限 | 审查可把整份 diff 灌进模型 | 质疑路径可加上限；施工审暂不改 |
| 原子写、SQLite、MCP、tunnel | 状态库、协议服务、ChatGPT 隧道 | 无 | **不借** |

质疑失败时用现有的 `infra_failed` 语义：没有有效质疑产出就不能把结论写成已支持。对应他们的 `FAIL_CLOSED`，不引入新状态。

### 8.2 mex：安装与可发现性

| 设计 | 他们怎么做 | 本仓现状 | 是否借 |
|---|---|---|---|
| 安装先预览 | `mex setup --dry-run`、`mex skills sync --dry-run` | `install.sh` 直接覆盖 kit、直接 `rm -rf` 后端 `skills` 再重建软链 | **借。** `--dry-run` 只打印将改动的路径；按工作流技能名管理入口，不删除用户自己的技能。该问题已由 `wf init` 不覆盖已有入口解决 |
| 托管块而不是整目录覆盖 | `<!-- mex-agent:skills:start -->` … `end`，冲突时报错让人处理 | 根 `AGENTS.md` 已存在则不覆盖，但技能目录会整棵删掉 | **借托管块思路用于技能入口，不改 AGENTS 全文覆盖策略** |
| `doctor` / `capabilities --json` | 机器可读：装了什么、索引是否新鲜、忽略规则是否正确 | 只有 `.workflow/VERSION` | **借一个小脚本。** 检查：kit 与 VERSION、软链、`workflow.env` 是否存在、`cursor-agent`/`codex`/`$WF_PY` 是否能跑、`WF_TEST_CMD` 能否启动、exclude 块是否在。给人看短文本，给脚本加 `--json` |
| 规范文件 / 派生索引 / 本机状态三分 | 知识进 git；`graph.db` 本机重建；draft 不进 git | 已有 ADR vs kit vs scratchpad | 保持现状。质疑报告留 scratchpad，结算后的结论进 ADR 或手册 |
| `plan` / `--apply`、签名预览 | 防止过期方案被执行 | 无 | **不借。** 质疑两轮上限已经限制扩张 |
| Hub、代码图谱、成员、遥测 | 本地 UI 与 SQLite 检索 | 无 | **不借** |

### 8.3 本仓已经有、只需保持的

- 机制副本与项目文档分离（`install.sh` 只覆盖 `kit/` 和 `VERSION`）。
- 超时与整树回收（`lib_timeout.sh`）。
- 流式日志、凭证打码、非 git 环境 fail-loud。
- 机器检查由脚本亲产，不信模型自述。
- 不自动 commit、不自动 push。

这些与两边的安全边界一致，不必重做。

### 8.4 对照测量本身

mex 的 `evaluate/compare` 把一次实验拆成 `--validate`、`--prepare`、`--run`、`--report`，支持 `--resume`，并拒绝把评测产物写进会污染被测仓库的目录。本次 MLM 对照是一次性脚本，放在 `/home/yh/ab-eval/`，隔离方式（git 浅副本、bubblewrap 藏真实项目、随机分组、两轮盲评）是对的。

固化到维护流程即可，不做成产品：

- 被测仓的隔离副本与真实项目分开；
- 评测产物不写进被测工作树；
- 步骤分开：还原上下文、跑两组、盲评、对照参考答案；
- 中断后可从已完成的组继续。

具体命令写在 MAINTAINERS 或本文第 6 步，不新增评测框架仓库。
