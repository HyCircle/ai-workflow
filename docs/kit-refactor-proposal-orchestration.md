# 提案：重构 planner 工作流，让编排重新对结果负责

状态：已认可，核心机制已于 2026-09-10 在本仓实施。本文保留问题分析与设计依据；现行操作以 `kit/` 和 [设计蓝图](design.md) 为准。真实项目长期效果仍待试用验证。

面向：workflow kit 维护者。适用范围：任务分诊、planner / worker / reviewer 的职责、派单输入、验收与复审、用户放行，以及相应脚本的信息回传。

**核心判断：当前 workflow 容易把“对最终结果负责”替换成“把工单展开完整、把审查意见逐条闭合”。临时实现获得了过高的约束力，planner 对整体实现的判断又被验收报告替代，真实反馈被推到流程末尾。厚工单、反复修补、黑话和低效的人审，是这些机制相互强化的后果。**

重构优先解决三件事：**让临时方案可撤回，让负责人拥有整体判断，让真实反馈提前到来。** 在此基础上，缩短工单、取消默认工单审、减少复审才会稳定地产生收益。

## 2. 实际发生了什么

### 2.1 目标是获得实验数据，工作却长期停在框架验收

原任务要求落地记忆质量评测的基础契约，并运行基线实验，为维度选择提供数据。planner 切出两张工单：先改评测契约，再搭实验框架。

第二张工单逐渐覆盖种子集、多个候选维度、逐条与分层评估、长表输出、探针、重复实验、统计汇总和 mock 测试。真实数据库与真实评委的运行被留给 planner，明确排除在该单成功判据之外（E1、E5）。

这张单经历两轮工单审、三轮完成的施工及双验收，第四轮施工派出后因内存不足被停止，随后由 planner 手工修复。不能把它写成“四轮施工审全部完成”。经过后续 session 的重搭，真正的基线采数与维度分析仍未完成（E2）。

### 2.2 最关键的矛盾在施工前已经被发现

实验要评“润色结果是否忠实于抽取句”，但现有润色评委只看到源对话和润色结果，不看到抽取句；工单同时禁止修改既有 `quality.py`。

第二轮工单审明确指出这个矛盾，还提出从实验侧把抽取句拼入评委消息的建议（E3）。planner 接受，将它写为不得擅改的“定夺 #4”（E1、E5）。

随后，施工审发现新输入污染了本应只对源对话判断的忠实度结果，并明确指出工单本身缺少保护（E4）。修法继续沿原方案展开：拆成两次评委调用、再调整各自的题干与结果消费。各轮处理的是实际问题，但没有及时重新比较整个方案。

**失败节点在于：发现实验要求、现有接口和改动边界之间有矛盾后，默认通过新增机制同时保住三者。** 当时还可以调整接口、单独设计候选维度实验，或暂缓该维度，这些选择没有得到充分比较。

提供抽取句本身并非错误：要评润色对抽取内容的保真，评委需要看到抽取内容。问题是把它挤入承担另一种判断的既有调用，并让“不能改上一张单的实现”主导了设计。

### 2.3 多轮验收没有消除真实路径与测试对象的错位

已提交的 `69538ba` 中，`assemble_memory_quality_verdict` 是供测试使用的合成函数，而实际入口 `evaluate_memory_quality` 另外内联了一套合成逻辑。后续 `f61926e` 才让实际入口调用同一份合成实现（E6）。

部分实际入口测试确实存在，不能说整个模块都没有真实路径覆盖。但那几条关键合成测试证明的是另一份实现；两份逻辑可以漂移，测试仍绿。

基线实验还出现过 HTTP mock 构造失败、真实客户端把异常转成错误结果，而测试只检查调用次数和 CSV 存在就通过的问题（E1）。这些是“证据支持不了结论”，无法靠测试数量或审查轮数弥补。

### 2.4 不能把所有审查意见都归为无效扩张

原始审查发现了缺答被记成最好分、统计混桶、评委失败被计入有效观测、被评文本未落盘等问题。这些会直接污染实验结论，修复有价值。

与此同时，planner 经常把 blocking 全部接受，把 nit 也升级为必修；最终工单保留原判据，再叠加多轮修复要求。用户明确反馈黑话过多、难以审阅（E1、E5）。问题在于缺少成本与方案层面的裁决，并非审查员发现了问题这件事本身。

## 3. 失效机制分析

以下是由上述事实与提示词结构推导出的机制解释。它们能解释这次失败，也能指导重构，但各因素的影响大小仍需通过真实任务试用判断。

### 3.1 目标逐层被替换成了流程内部的完成条件

用户需要可信的实验结果。worker 被要求交出满足工单的实现，reviewer 被要求逐条找证据，planner 被要求裁决 findings。每一步都可以完成，最终目标却仍未得到验证。

当前 [planner skill](../kit/skills/planner/SKILL.md) 把“读验收单代替读 diff”作为节约上下文的重要机制，亲验位置主要由 reviewer 推荐。这样可以降低局部任务的阅读成本，但也会让 planner 的视野继承 reviewer 的遗漏。

问题不要求通过“planner 必须亲自写所有代码”解决。需要的是：无论谁实现，总有一个负责人理解实际入口、核心数据流、主要设计选择和证据的局限，并持续检查当前工作是否在推进用户目标。

### 3.2 临时做法被抬升为冻结契约

ADR、未验证假设与本轮实现建议具有不同约束力。实际工单却把“冻结契约”和“planner 定夺”放在同一标题下，要求不得擅改（E5）。

ADR-0007 把输入携带方式、字段名等留给实现，把润色保真列为候选；后续却把上一张单的 API 与本轮注入方法当成必须保住的前提。修改这些做法逐渐像修改用户决定一样沉重。

当前 skill 已有“冻决策，不冻 HOW”的说明，也允许坏设计转 ADR。但继续修码有直接可执行的复审路径，调整设计则容易被理解为报告、请示、著作与重新冻结。两条路径的成本不对称，使修补成为默认。

### 3.3 完整性要求与审查激励共同推动扩张

[工单模板](../kit/skills/planner/WO-TEMPLATE.md)要求预判陷阱；planner 对 HOW 完整性负责；[工单审](../kit/skills/planner/wo-review-preamble.md)要求每个失效模式都有判据，还要主动补 ADR 没想到的边界。这些局部要求叠加，容易使“可指出的不足”直接变成新增任务。

现有规则实际上允许驳回，也写了默认一轮复审和坏设计处置。问题并非完全没有出口，而是没有把“这条意见值得修吗、该怎样修、是否应换方案”落实为主要判断动作。执行记录中的全盘接受进一步放大了这种倾向。

### 3.4 模型异构没有解除共同的审查框架

[施工审提示词](../kit/skills/planner/review-preamble.md)明确允许审工单本身，原始报告也确实这么做了。因此“验收只查合规”不准确。

但多个角色都从同一份工单及其判据出发。换模型可以补实现层面的盲点，不能保证它们独立质疑同一组设计前提。多轮审查可能把局部要求查得更细，而整体方案仍无人重新判断。

需要把审查证据重新连到用户目标和实际行为；不能把独立性简化为模型家族不同。

### 3.5 自动断言的明确性被误当成验证有效性

最终工单为了验证探针未编造信息，要求断言文本不包含“持续、希望、计划”等外推词，并让 worker 按种子选择词表（E5）。这条测试能失败，却无法证明没有编造：源句可能确实包含这些词，编造也不必使用它们。

“bug 在时会红”有价值，但仍须说明测试覆盖哪个真实失败、经过什么实际路径。语义判断、测量设计与模型行为，有些需要样本审阅或真实实验，不能为了给工单配自动验收而制造替代指标。

### 3.6 按组件切任务，把最有价值的反馈放到了最后

完整实验框架的验收早于第一小批真实样本。于是输入是否合理、评委是否理解题目、输出是否足够支持分析等关键问题，要等框架与测试全部完成才得到反馈。

一次性工具同样需要可靠的数据处理；“以后肉眼看 CSV”不能替代对采集链的验证。正确的减法是先获得一条可信的完整路径，再决定值得扩展哪些功能。

### 3.7 表达问题降低了人和 agent 的纠偏能力

跨轮编号和术语本身可以帮助定位，但不能替代完整含义。原工单逐轮保留旧要求、引入新编号，使人需要恢复整段历史才能理解当前选择。

只让用户扫一行意图，只能确认任务大类，无法审查新增输入、暂缓的实验、实现取舍和未验证部分。用户收到放行请求，却缺少足够清楚的决策材料。

黑话对跨 agent 理解造成多大损失，本次没有量化证据；用户可审阅性下降则有直接反馈。改进应要求平实、自足的当前说明，不再建立“术语数量达标”的新闸门。

## 4. 对旧提案和后续自审的修正

| 原判断 | 本次判断 |
|---|---|
| 错误前提穿过全部审，几轮以后才被发现 | 接口矛盾在施工前已被指出；首轮施工审也发现了工单导致的污染。主要失败是如何处理已发现的矛盾。 |
| 工单审散文必然导致退化 | 默认全量审查有扩张倾向，但本次也提前发现了真实错误。取消默认流程不等于否定定向方案审查。 |
| 当前流程没有驳回或重想出口 | 有驳回、软上限和坏设计处置，但默认动作与上下文组织仍推动继续修补。 |
| 三档分诊只按行数切 | 当前还考虑边界、风险、热路径与实验；缺陷是把设计不确定性、规模和风险混入同一条重流程。 |
| `triggered` 残留证明冷 worker 重写导致质量差 | 记录显示第 4 轮 worker 未改文件；残留发生在 planner 自己做文本替换时。不能据此归因给 worker。 |
| OOM 证明多 agent 并发就是根因 | 只确认任务因内存不足停止；缺少进程与资源数据，不能确定完整原因。 |
| 重搭后的行数和测试数下降证明同功能质量提升 | 重搭还删了候选维度和统计功能，范围也缩小了。结构修复成立，整体实验效果仍待验证。 |
| 手动流程好，说明差别全在编排 | 手动经验支持改进编排，但范围选择、执行自由度、人的判断与审查方式也同时变化，不能把贡献全归给提示长度。 |

这些修正影响重构方向：不能用“少审、少测、少写”替代对证据与整体方案的判断，也不能把一次后续自审当成新的不可质疑前提。

## 5. 重构后的工作方式

### 5.1 planner 对结果负责，自主选择执行方式

planner 的主要职责改为：理解目标与现状，识别关键不确定性，安排最能提供反馈的下一步，整合证据，对最终结果作判断。

模型成本仍要考虑，但衡量整个任务的外呼、返工、用户负担和完成质量，不能只优化 planner 读了多少 token。planner 可以自己写，也可以委派；委派探索任务同样有效，只要交付的是具体证据与结论，而非假装方案已经确定的施工规格。

### 5.2 把分诊拆成三个独立判断

| 判断 | 问什么 | 对工作方式的影响 |
|---|---|---|
| 设计不确定性 | 哪个关键假设尚未验证？什么反馈能确认或推翻它？ | 优先安排读实况、样本分析或最小可运行实验。 |
| 改动风险 | 错了影响什么？是否容易发现、恢复？ | 决定验证强度、是否需要独立审查及用户批准。 |
| 委派收益 | 任务边界是否能传清？上下文交接成本是否低于直接完成？ | 决定自做、委派或并行，行数只作参考。 |

探索型任务可以高风险，也可以低风险；机械任务也可能高风险。不要因为“含实验”自动套全模板与双验收，也不要因为“设计没定”一律禁止派 worker。

### 5.3 派单以短 brief 为默认，明确哪些可以改

每份派单输入应让执行者和用户读完后理解以下信息；简单任务可合并为几句话，不要求逐项铺开模板。

```text
目标：这次要实现的行为，或需要回答的问题。
依据与边界：相关代码/数据/ADR 指针；已确定、此次必须保留的要求。
待验证：尚不确定的假设；如无则省略。
交付与证据：可运行结果、样本或检查，及它能证明什么。
做法建议：仅在有帮助时给出；执行者可在授权边界内调整并说明原因。
```

ADR 引用和意图定位保留，但不能代替实际目标，也不要求无关的小修为派单新造 ADR。默认 brief 应可在一次简短阅读中理解；必要的技术细节放在已有代码、数据或独立规格的指针里，不用硬字数上限逼出缩写。

用户决定和已接受契约约束行为；未验证假设必须标明；实现建议默认可调整。撤回 planner 自己提出的做法，不自动等于修改 ADR。只有确实改变已接受契约、用户目标或授权边界，才需要相应设计与批准流程。

### 5.4 先建立最小完整反馈，再扩大实现

探索型任务的默认顺序：明确问题 → 获得第一份真实证据 → 判断方案 → 扩大实现 → 验证结果。

在本案例中，合适的第一步可以是少量源对话贯穿生成、评委和结果落盘，检查评委实际看到了什么、返回了什么、能否用于下一步分析。无需先完成全部维度、统计汇总与测试网。

第一份证据必须针对当前不确定性：纯接口问题可用实际入口加受控响应验证；模型语义问题需要真实评委样本；数据库接线需要相应环境的运行。薄实验不必每次都访问外部系统，但必须说明替代了什么、还不能证明什么。

环境不可用时，继续完成独立的准备工作，并明确未验证部分与环境需求。框架通过、测试通过、真实结果可用应分别陈述。

### 5.5 worker 保留实现判断，矛盾能及时返回负责人

worker 在目标与硬边界内选择实现，不因 brief 写了一个建议就被迫加兼容层或字符串手术。发现必须改变任务范围、关键假设不成立，或完成该做法需要显著新增机制时，报告具体矛盾与可行选择。

报告只需说明结果与证据、重要偏离、待定问题。正常的局部实现选择无需反复请示；真正阻塞设计的矛盾不能等所有实现和验收完成后才让 planner 看见。

### 5.6 审查围绕实际行为与高价值疑点组织

取消“凡全量模板必先审 WO”的默认流程。只有某个未经验证的选择一旦错了返工代价明显较大，或用户显式要求时，安排定向方案审查，给出具体问题及事实源。

施工审先判断实际行为是否满足目标、实现是否引入不必要机制、测试是否经过真实路径；工单条目是辅助，不是唯一结构。保留审查工单本身的权限，但不要求把所有可能边界都补成测试。

每条重要 finding 应给出实际或可信的触发条件、错误结果与依据。需要区分已经确认的缺陷和待验证疑点；纯改进建议不自动阻断。不能只因“缺一条断言”就升级为 blocking，也不能因没有自动测试就忽略真实风险。

独立审查按风险选择。默认不因多文件或含实验启用双验收；第二审应有明确的额外价值，例如独立检查测量口径或高风险写入路径。无需为每个角色再建立固定专项流程。

### 5.7 planner 自己核实整体，不把判断交给报告

放行前，planner 应能说明：实际入口如何走到核心行为；主要测试替代了哪些环节；最重要的设计选择为什么成立；结果如何支持用户的下一步。

简单局部修改可短读相关代码和结果。新模块、核心数据流或多轮返工，应看整体结构与关键调用链，必要时独立选择样本核实。reviewer 推荐的 0–3 处代码是线索，不是亲验范围上限。

测试全绿证明执行过的断言成立；无 blocking 证明此次审查没有报告阻断问题。两者都不直接等于用户目标已经达成。

### 5.8 复审前先判断继续修是否合理

负责人对问题可选择：修实现、调整或撤回本轮方案、给理由不采纳、在确实改变硬契约时转设计决策。认可问题存在，不等于接受 reviewer 提出的修法。

以下情况应暂停自动修复，重新判断方案：

- 同一设计矛盾换了几种表现反复出现。
- 修一处需要新增调用、转换层或平行实现，又产生新的不一致。
- 关键假设已被证据推翻，继续施工仍把它当作前提。
- 复审越来越细，却迟迟没有获得支持用户目标的新证据。

轮数只作提醒。第二轮仍未收敛时，简短说明剩余问题属于局部缺陷还是方案问题，以及继续的依据；不把“一轮有新 finding”或“两轮未结束”机械等同于切法错误。

复派时重写当前有效的 brief，撤回过时要求。旧版本与审查原文留在 run 记录中，不让执行者同时满足多代方案。局部小修可由持有上下文的 planner 直接完成，再做匹配风险的验证。

### 5.9 用户放行面对具体选择，日常判断仍由 agent 承担

需要用户决定时，提供简短材料：当前结果或拟选方案、关键依据、主要取舍、尚未验证的部分，以及这次需要用户决定什么。意图行仅作为定位辅助。

在既有授权内调整实现、修复缺陷或撤回自己的建议，planner 自主处理并说明重要变化。涉及目标、范围、硬契约、外部副作用或明确约定的 commit 放行时，遵循对应授权要求。重构不增加每轮都必须人审的新仪式。

脚本层需要特别澄清：

- **`WO_REVIEW` 当前默认已经是 `0`。** 默认工单审来自 skill 主动调用 `WO_REVIEW=1`，不是脚本开关默认值。实施时应先改流程要求，保留显式调用能力即可。
- **四态继续从机器事实与审查产物派生。** 不把“待验证假设”塞成新的自动放行状态，也不让 `review_complete` 宣称业务目标完成。
- **worker 矛盾回传先复用已有路径。** 当前 `SKIP_REVIEW=1` 已能执行后返回，但同时跳过脚本的 pytest 和文档检查，且回显不包含 worker 报告。探索任务可先用这一入口，由 planner 主动读取 `report.md` 并安排适合该实验的检查；需要独立审查时再用 `REVIEW_ONLY=1`。脚本改动优先补清晰的报告回传与未执行检查说明，不预设必须增加新模式或报告协议。
- **意图定位支持任务目标，不强迫制造 ADR。** 当前入口强制出现 `ADR-NNNN`。拟改为要求明确目标，有相关 ADR 时引用并遵循它；无相关 ADR 时允许说明所承接的用户任务。文本校验不等于授权证明，也不自动证明语义对齐。同步更新入口测试，覆盖现有 ADR 工单、无 ADR 的有效目标、空目标被拒绝。
- **brief 快照与报告复用现有 run 目录。** 不另建裁决台账、跨轮状态数据库或强制检查清单。保存本轮输入后，执行与验收应使用同一份快照。

## 7. 保留的能力与明确不做的事

保留外呼封装、后台派发、超时与错误暴露、打码、用量记录、著作文件越界检查、实际测试与文档检查，以及适用时的独立验收。保留 ADR 对长期契约的记录、scratchpad 与长期资产分离、用户约定的提交授权。

多 agent 委派继续是可选执行方式：适用于机械铺开，也适用于边界清楚的调查、实验或独立审阅。其价值由任务收益判断，不以“必须机械且有自动验收”为资格限制。

本提案不要求所有任务由强模型亲写，不要求每次都跑 live，不取消必要测试，不增加固定轮数停工闸、不设置术语计数器，也不靠添加更多状态与角色来保证判断。维持一个负责人连续承担结果责任；session 长度与压缩方式按实际上下文需要选择。

## 8. 实施顺序

### 第一步：统一职责和默认路径

一起更新 planner skill、brief 模板与三个 preamble，消除“实现可调整”与“定夺不得擅改”、“结果审查”与“逐条完整性审查”之间的冲突。同时同步设计文档，避免两套工作流并存。

这一阶段先使用现有脚本能力安排执行与审查，不以新增脚本协议作为前提。入口尚未更新时，无相关 ADR 的小修按自做路径处理，不填虚假 ADR 绕过校验。用户仍可显式要求工单审或双验收能力。

### 第二步：补齐必要的信息回传

实现 brief 快照、worker 结果与矛盾可见，完善探索任务执行后返回负责人的路径，并调整意图入口。保留现有机器事实与错误语义，避免顺手重写 derive、超时、越界等无关机制。

涉及脚本时按维护约定运行 `bash kit/scripts/tests/run-all.sh`。新测试针对新增行为及真实失败：执行/验收消费同一输入、矛盾报告可见、探索执行未被误标为验收通过；不要为文案逐句建立断言。

### 第三步：在真实任务中试用，再调整默认值

选择边界清楚的局部实现、需要发现设计的实验、高风险但方案明确的改动，观察新流程是否分别采取合适的执行与验证方式。

修改在本仓完成，经 `install.sh` 投影消费仓。无需复制项目历史进 kit，也不在消费仓投影副本上维护另一套规则。

## 9. 如何判断重构有效

### 9.1 用本案例检查新规则能否改变关键决策

这是设计回放，不冒充真实对照实验。维护者检查新流程是否允许并鼓励以下行为：

| 触发点 | 新流程应支持的反应 |
|---|---|
| 评委看不到候选维需要的抽取句 | 比较改接口、独立实验、暂缓维度；既有 API 不自动升为用户契约。 |
| 需要完整框架前才能采第一份数据 | 先选择少量样本贯穿关键路径，验证测量是否有意义。 |
| 测试只调用另一套合成函数 | 追踪实际入口，让证据覆盖实际行为，不用测试数补信心。 |
| reviewer 报告缺陷并建议新增一层机制 | 接受缺陷事实后独立判断修法，允许撤回方案。 |
| 第二轮仍有问题 | 根据矛盾类型和已有证据决定小修或重想，不按轮数自动停工或重派。 |
| 用户需要放行 | 展示具体取舍、证据与未验证部分，用户不必恢复整份工单历史。 |

### 9.2 用结果与成本共同评价真实试用

首要问题是：用户目标是否完成，关键结果是否可信，交付后是否还出现真实路径缺陷。其次看达到这些结果的代价。

可从已有 transcript、run 日志和交付物中抽样记录：

- 获得第一份能验证关键假设的证据用了多久。
- 获得最终可用结果用了多少时间、外呼与用户干预。
- 返工在修局部缺陷，还是反复维护同一错误前提。
- 验收结论是否明确区分已测、替代测试与尚未验证。
- 用户能否看懂本轮方案、主要取舍和下一步决定。

工单长度、审查轮数、代码和测试行数只作诊断线索，不作为质量目标。比较任务时记录范围变化；删掉功能后的缩减不能全部记为同功能效率提升。也不能把 findings 变少当成质量提高——可能只是少查出了问题。

无需先建立新指标平台。先用少量真实任务和现有记录判断：**流程是否更早获得了有效反馈，是否更容易撤回不成立的方案，是否以更低的总成本交出了可信结果。**

## 10. 本轮实施与验证

已重写 planner skill、短 brief 模板与三个 preamble，澄清 discipline 的契约/实现边界和证据要求，并同步 BS 交棒、人审说明、模型配置注释及维护者文档。

脚本沿用四种模式：接受无 ADR 的非空目标，保存 `brief.md` 供执行和审查共同使用，回显 worker 报告，明确跳过的检查。探索复用 `SKIP_REVIEW=1`，再按需要 `REVIEW_ONLY=1`，没有增加模式或跨轮状态机。检查中发现的“测试失败但无 FAILED 行导致报告中断”也已修复。

- `WF_PY=python3 bash kit/scripts/tests/run-all.sh` 全部通过，涵盖派生、外呼错误与超时、目标入口、四种派单模式及显式双审、实际机器检查失败、安装投影与 staged 文档检查。
