# Holistic(整体审)

先读 discipline 和 AGENTS，全程中文。单个 ADR 和单张工单只看局部；你回答的是：把所有决定放在一起，这个项目现在还是一个简单、自洽的设计吗？

## 读什么

- architecture 全文、decisions 下全部 ADR、TODO。
- 代码：实际入口、核心数据流和模块边界；按 ADR 涉及的契约抽查实现。用 `git log` 找近期改动最频繁的区域重点读。
- patterns 与近期归档按需读。

范围大时按模块分批，汇报写明覆盖了什么。

## 找什么

1. **冲突**：两份 ADR 之间、ADR 与代码、architecture 与实况说法不一致。
2. **重叠**：同一主题散在多份 ADR；一个决定在多处复述。
3. **接缝**：各 ADR 单独成立、合在一起出问题的地方，零碎 bug 常聚在这里。能复现就复现。
4. **多余复杂度**：为单个决定局部最优而加的层、配置和兼容路径；没有真实消费者的机制；可以用更通用的数据表示统一掉的多套做法。
5. **过时**：已不再适用的决定与文档。

每条发现写涉及的 ADR 或文件、问题、依据(代码位置或复现结果)。没有证据的标为待验证。

## 方案

在发现之上给一份整体方案，而不是逐条补丁：

- 目标设计：一两句话说清整理后系统是什么样；
- ADR：合并、改写、删除清单，整理后每个主题一份；
- 代码：删除与合并项；
- architecture：怎么改成与目标设计一致的全局图。

按收益排序，每项标出风险和所需验证。方案写到 `.workflow/scratchpad/HO-<完整 session UUID>/plan.md`，回复里简述并请用户确认要执行哪些。

## 执行

按用户确认的范围执行。ADR 原地修改或删除，删除时清掉对应的 `ADR-NNNN` 引用；architecture 同步为整理后的全局现状；代码改动跑测试并验证实际入口。代码改动量大时交 `/planner` 安排。汇报区分实现完成、检查通过与真实结果已验证，并列出未执行的方案项。
